Curator 0.43.0 → proposal, revision 3

Status, import and re-match on the item page

Revised after Fable's design review. Three additions to a movie or series page in curator: a panel that shows exactly where the item stands from search through to cinema, an Import button that takes you straight to a file browser, and a Re-match action for when something was matched to the wrong title or episode. Nothing is built yet. The mocks below are drawn in curator's own colours and switch between desktop and phone width.

What the review changed. Fable checked this against curator's code, its ADRs, the contract v2 docs and runner's source. Verdict: approve with changes; re-match reworked.

  • Re-match is now one operation, move files to the right item or episode, instead of rewriting an item's identity in place. Rewriting in place would have carried the wrong title's blocklist, history and in-flight grabs onto the right one, and deleted an item you still wanted.
  • Telling cinema to drop the old folder needs a contract change and a cinema change: today a scan of a path that no longer exists retries forever. Both are now in the plan.
  • Moving a wrong file now blocklists the release that produced it, so the vacated episode doesn't grab the same release again.
  • Importing a runner delivery by hand goes through the existing Resolve path, so curator's own cleanup rules handle the original and there is no delete checkbox.
  • ETA and post-processing progress come from runner's own numbers instead of curator recomputing them. Runner has no queue position or unpack progress, so the panel says "queued" and "unpacking" without numbers rather than guessing.
  • The panel never hides itself, and cinema's state reads "confirmed at" a time rather than "available now".

Backend

  • One endpoint, GET /library/{id}/status, built as a read projection in acquisition beside the queue and import activity views, since that is where downloads, publications and deliveries live. Series return season summaries; ?season=N returns that season's episodes. Mobile uses the same calls. history_events gets an index on the item.
  • One search record per movie or episode. Written inside the shared search-and-grab path, so auto search, the background automation, Wanted runs and interactive grabs all land in it: time, trigger, counts seen/matched/accepted, top rejection reason, the download it led to. Wanted runs read their per-target counts from it instead of keeping their own. Newest 20 kept.
  • Runner's numbers, relayed. Curator's runner adapter carries rate_bps and remaining_bytes through; ETA is their ratio. Verify and repair progress come from runner's existing fields. Curator never guesses runner's scheduler, so a queued job says "queued".
  • Per-file cinema results. Cinema's read-back already reports each expected file as placed, skipped or missing; curator stores that per file, so each episode in a pack gets its own In-cinema state.
  • Refresh. The active download polls every 2 s; the rest of the panel every 30 s; neither moves scroll or focus.

Behaviour

  • Every failure says what went wrong in plain words and offers the one action that fixes it: search again, retry import, send to cinema again, or import a file by hand.
  • When cinema is slow, the panel shows the reason cinema gives (a full scan, the heavy-work lane, an unreadable root, its queue position), so a wait is attributable from inside the product.
  • Earlier attempts (a failed grab, a blocklisted release) fold into an "Earlier attempts" list under the track.
  • The panel never hides. Once everything is done it collapses to one line ("In cinema, confirmed Sep 4"). For items that predate this record, it shows the last known facts and offers Ask cinema to confirm, which sends a scan request with the item's files as expected files.
  • Mobile gets the same visible-result checks as web (every action's result on screen, at 390 px).
  • The Activity page keeps its full lifecycle trace; the item panel links into it for depth.
2 · Import

Import file… from the item page

Today, importing one file for a movie you already have takes about eight actions over two pages: Activity, Resolve, type a path into a box that only completes folders, Scan, tick the file, find the movie in a dropdown of the whole library, Queue. On the item page the target is already known, so it becomes: Import file…, browse, pick, confirm.

Import into Slow Horses

How it works

  • Browser. Folders come from /filesystem as today. The files in the current folder come from /import/scan limited to one level, which already returns size, quality, SxxEyy and file identity. It opens at the completed folder, with shortcuts to the item's own folder and the library roots, and a path box for anywhere else. A path curator can't see gives a plain error that says so and names the path-mapping fix.
  • Runner deliveries. A file inside a runner delivery goes through the existing Resolve placement, extended with a target item and episode. Its record, cleanup and Resolve listing all stay consistent; curator removes the original under its existing cleanup rules.
  • Loose files. Anything else goes through POST /import/manual with the item fixed: the same durable job, identity checks and cinema notification as an automatic import. Hardlinked when kept, so your copy stays; renamed only if you tick Remove original. Copies across volumes show bytes and Stop in the status panel.
  • Episodes, copies, editions. Each file gets an episode picker prefilled from its name, which also handles obfuscated names. The choice is sealed into the import attempt by path. Items with quality copies or book editions get a copy or edition picker.
  • Subtitles. Sidecar subtitles travel with the file, using the same code the claude/no-wedge branch adds for runner deliveries.

What the confirm step tells you

  • The exact destination path, built from the naming template.
  • What happens to a file already there: replaced if the new one ranks higher in the item's profile, otherwise kept beside it, with the reason.
  • For runner deliveries: that curator will clean up the original once it is placed, as for automatic imports.
  • For loose files: a Remove original option, off by default, and whether it will be a hardlink, a rename or a copy.

Activity's Resolve flow stays for folders that aren't tied to an item yet, and opens this same dialog once you've picked the target.

3 · Re-match

Fixing a wrong match

There is no way to do this today short of removing the file from the library and importing it again. Both shapes of a wrong match use one operation: move these files to the right item or episode, adding that item to the library if it isn't there.

  • Re-match… on the item page moves all of the item's files. The folder was adopted as Dune (1984) but it is Dune (2021): the files go to Dune (2021). For a series, every file gets an episode in the new series.
  • Move to… on one file in the Files panel moves just that file, to another episode or another title.
  • The item the files leave keeps its own identity and history. If you added it because you want it, it stays in the library as wanted. If folder adoption created it and it is now empty, it is removed. The preview says which.
Re-match Dune (1984)

How it works

  • Lives beside placement. The operation sits in acquisition next to file removal and import placement, as a new kind of journaled placement operation. A crash halfway resumes from the journal, so nothing is left half-moved.
  • Fenced. It takes the title lease on both items and refuses while either has a download in flight, an import running or a replacement operation open, with a message naming which and a way to wait for it.
  • Rename or copy. A rename when both folders are on one volume; across volumes (say /20t to /10t) a verified copy that shows bytes and Stop in the status panel, then the original removed.
  • Cinema sees both sides. A scan of the new folder with expected files, so the read-back confirms it. Removing the old entry needs new cinema support (below), because today a scan of a folder that no longer exists retries forever.
  • One folder per item (ADR 0020): the target folder carries the {tmdb-N} hint, so scanning and adoption keep the new match.

Guarding the change

  • The preview lists every rename before anything happens. Files that don't fit the new title (an episode number the new series doesn't have) are listed with a picker, or left out; left-out files stay on disk, removed from the library. A file covering two episodes maps to two episodes.
  • The release behind a moved file is blocklisted for the item or episode it left, through the existing replacement path, so the vacated wantable doesn't grab it again.
  • Books move between editions the same way; manual entries can be sources or targets, since nothing here needs a provider.
  • Nothing new remembers the wrong pairing: the blocklist entry and the {tmdb-N} folder hint are what stop the same match recurring. A rematched history event records from, to and every path that moved.
  • Written up as ADR 0027 before code, since it touches placement, scan and the contract-v2 publication records.
4 · Order of work

Curator in three PRs, plus one contract fix in cinema

  1. 0.44.0 Curator status panel: one search record, the adapter carrying runner's rate and remaining bytes, per-file cinema results, GET /library/{id}/status, the panel on web and mobile.
  2. 0.45.0 Curator import: one-level browse listing, Resolve placement with a target, loose-file import with episode, copy and edition choice, subtitles, Stop.
  3. Contract An amendment for files leaving a folder: curator names the removed paths on a scan of the parent and cinema answers each as gone; a sub-delivery keyed by operation instead of by publication.
  4. Cinema The matching change on cinema's side, in its own pipeline-v2 task PR.
  5. 0.46.0 Curator re-match: ADR 0027 first, then the move operation, Re-match… and Move to… on web and mobile.

Status can start now. Import and re-match touch the import code that the claude/no-wedge branch is rewriting, so they start from main after it merges. Re-match ships after the cinema change, so a move never leaves cinema with a stale entry.

Two calls I made that you may want to change

The item files leave behind. It stays as wanted if you added it, and is removed only if folder adoption created it and it is now empty. The alternative is always asking.

Re-match on a series moves every file at once. Splitting a series (some seasons belong to another show) goes through Move to… on each file instead, which is slower but rare.
