# Security checks — what runs and what the badges mean

Companion to the [security policy](../SECURITY.md) (private reporting) and
[README](../README.md) (installation and normal CI).

## Automated checks

| Check | Trigger | Evidence and interpretation |
|---|---|---|
| OpenSSF Scorecard | Push to `main`, Monday 08:23 UTC | Public practice score, SARIF artifact retained 14 days, Security tab findings. Inspect each check; the aggregate is not a vulnerability clearance. |
| CodeQL Go | Pull requests, `main`, Monday 08:41 UTC, manual dispatch | Builds the server and runs extended security queries. Findings appear under code scanning; successful execution is not a promise of zero findings. |
| CodeQL JavaScript/TypeScript | Same as Go | Source analysis covers the web, mobile and test source without installing or executing npm dependencies. Rust is not covered by these CodeQL jobs. |
| Dependency review | Pull requests | Rejects dependency changes introducing known high or critical vulnerabilities. Existing vulnerabilities require separate review. |
| Dependabot | Weekly | Update PRs for Go, all three npm lockfiles, the Rust encoder, Python reference requirements, GitHub Actions and Dockerfiles. Updates are reviewed through normal CI; none are automatically merged. |
| Existing tests, lint, compatibility, image build | Pull requests and `main` | Behavior and build checks remain separate from security analysis. |

All workflow Action references are pinned to full commit SHAs. Dependabot
maintains those pins. Checkouts do not retain write credentials. New security
jobs and all pull-request jobs use GitHub-hosted Ubuntu runners. Main-branch
builds also use fresh hosted VMs under the [CI policy](CI_POLICY.md). Hosted Go tests use
eight race shards. Playwright installs its browser dependencies in each fresh
job, and Go caching uses the hosted cache service.

Scorecard publication follows the upstream restrictions: a dedicated hosted
job, only approved Actions, no shell steps, no PR trigger, and write
permissions limited to code scanning and its OIDC publication token. It uses
the default GitHub token, not a personal access token. Publication sends
public repository security-practice results to OpenSSF.

## Reading badges and results

The workflow badges link to `pjunod/curator`. Coverage remains the committed
SVG generated by the existing test gate. The license badge links to the
actual GPL-3.0 license. The release badge reads GitHub Releases; a Git tag or
`VERSION` alone is not a published release. No GitHub Release existed during
setup on 2026-11-13, so an empty/no-release result is expected until one is
published.

The numeric Scorecard badge needs a successful published default-branch run.
Before that run it may show no data. The pinned Scorecard Action v2.5.0 can
warn rather than fail when publication fails: verify the public viewer as
well as the workflow result. SARIF remains the retained scan evidence.

CodeQL can successfully complete while reporting vulnerabilities. Read
Security > Code scanning, triage the findings, and configure required checks
or code-scanning merge protection deliberately. Do not interpret a green
Security workflow badge as an assertion of zero vulnerabilities.

## Repository settings and remaining work

Repository settings are separate from these workflow files. The setup
receipt records the observed and changed state; inspect GitHub for the
current state. Private vulnerability reporting, dependency alerts,
Dependabot security updates, secret scanning and push protection should be
enabled so the policy and dependency checks have working services behind
them. These were enabled on 2026-11-13. The repository default workflow token
was changed to read-only and Actions may no longer approve pull requests.
Workflow approval is required for all external contributors. Review workflow
edits before approving runs: runner selection in a PR-editable workflow does
not prevent a malicious workflow from targeting an available lab runner.
Stronger runner-group isolation remains a separate infrastructure decision.

No branch protection or repository ruleset existed at inspection. This change
does not impose required approvals on a solo maintainer. Select required CI
contexts after the new workflow has run; review policy must allow the owner
to maintain the repository without weakening ordinary checks.

Remaining security work includes reviewed release signing/provenance,
container vulnerability scans, Rust static analysis, continuous fuzzing, and
an evidence-backed OpenSSF Best Practices assessment. These are not claimed
by adding Scorecard. A public numeric score may remain limited until those
practices and repository controls exist.

## Authentication and proxy transport

New passwords use the Go standard library's PBKDF2-HMAC-SHA-256 with 600,000
iterations, a fresh 16-byte random salt and a 32-byte key. This work factor
follows the [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2).
The version, parameters, salt and key share one `auth_password_hash` value,
so a failed credential write cannot leave a new salt with an old hash.
The implementation makes no FIPS certification claim.

Existing salted SHA-256 credentials still work. Only a successful login
upgrades them; a failed upgrade write leaves the previous credentials
usable and logs a warning without secrets, then retries on the next login.
Unknown hash formats fail closed. Login and credential updates serialize
within the server so a migration cannot overwrite a concurrent password
change. Backups made before migration retain their old password protection.
A downgrade to a server predating this format cannot verify upgraded
credentials; retain an API key for recovery or restore an appropriate backup.

Session cookies are HttpOnly and SameSite=Lax. Both login and logout set
Secure for direct TLS. Plain LAN HTTP stays supported and therefore does not
set Secure; use HTTPS when transport confidentiality is required.

Behind an HTTPS proxy, set `MONARR_TRUSTED_PROXIES` to the immediate proxy's
CIDR addresses, for example `192.0.2.10/32,2001:db8::10/128`. The optional
JSON config uses `"trustedProxies": ["192.0.2.10/32"]`. Restart after changing
process configuration. Trust defaults to empty. Choose narrow ranges and
restrict direct access to the service. The trusted proxy must **overwrite**
`X-Forwarded-Proto` with exactly `https` or `http`; it must never preserve
client-supplied values. Curator ignores this header from untrusted peers and
rejects comma-separated or repeated scheme headers. `Forwarded` and
`X-Forwarded-For` do not grant trust.

`TestLegacyLoginMigratesOnlyOnSuccess`,
`TestMigrationWriteFailureRetainsUsableCredentials`,
`TestPasswordChangeIsOneAtomicHashWrite` and
`TestSessionCookieTransportBoundary` verify migration, write failure,
password replacement and the LAN/TLS/proxy boundary. Conditional Secure
handling and the legacy verifier may still appear in static analysis;
neither warrants suppressing the scans or breaking supported HTTP installs.
